## 과제: 개인화 QT 시스템의 "빈틈 없음" 수학적 증명

### 시스템 변수
- 온보딩 설문: 12문항 (Q1은 0점, Q2-Q12는 각 0-3점, 총 0-27점)
- 성숙도 4단계: 입문(0-6), 초급(7-13), 중급(14-20), 심화(21-27)
- 선택 가능 주제: 140개 (7개 카테고리)
- 묵상 분량: 3종 (짧음/보통/많음)
- 병행 읽기: 2종 (병행/한권씩)
- 동적 페널티 알고리즘으로 주제 순서 결정

### 증명해야 할 것

1. **조합 완전성**: 위 변수의 모든 조합에서 유효한 플랜이 생성되는가?
   - 성숙도 4 × 분량 3 × 병행 2 = 24가지 설정 조합
   - 각 조합에서 140개 주제 중 어떤 것을 선택해도 30일 플랜이 생성되는지
   - 빈 플랜이 나오는 경우가 있는지 (데이터 없는 주제 등)

2. **순서 유일성**: 동적 페널티 알고리즘이 같은 입력에 대해 항상 같은 순서를 반환하는가?
   - 동점일 때의 다중 조건 정렬(영적 환기 우대 → 발달 순서 → 선택 순서)이 결정적(deterministic)인가?
   - 같은 점수의 두 주제가 있으면 결과가 비결정적인가?

3. **개인화 차별성**: 서로 다른 사용자가 실제로 다른 경험을 받는가?
   - 성숙도가 다르면 같은 주제라도 가이드 내용이 다른가? (입문 vs 심화)
   - 같은 3개 주제를 다른 순서로 선택하면 플랜이 달라지는가?
   - 최소 몇 가지 입력 차이가 있어야 다른 플랜이 나오는가?

4. **경계값 테스트**:
   - 주제 0개 선택 (가능한가? 방지해야 하는가?)
   - 주제 140개 전부 선택
   - 같은 카테고리에서만 10개 선택
   - 점수 정확히 경계 (6점 = 입문 vs 7점 = 초급)
   - 모든 위기 주제만 선택
   - is_heavy 주제만 5개 선택 + 분량 "짧음"

5. **데이터 의존성 맵**:
   - 어떤 주제를 선택하면 어떤 JSON 파일이 필요한지 의존성 그래프
   - 현재 상태: 10개 주제는 qt-guides-topicN.json (풀 가이드), 나머지 130개는 curricula-extended.json (구절만)
   - 풀 가이드가 없는 주제를 선택했을 때의 폴백(fallback) 전략
   - 폴백 시 사용자 경험이 얼마나 저하되는가?

6. **알고리즘 복잡도 분석**:
   - 140개 주제 전체 선택 시 정렬 알고리즘의 시간 복잡도
   - 프론트엔드(JavaScript)에서 실행 가능한 수준인가?
   - 병목 지점이 있다면?

### 출력 형태
- 각 증명에 대한 논리적 분석
- 빈틈이 발견되면: 정확히 어떤 입력 조합에서 실패하는지
- "커버리지 매트릭스" (성숙도 × 카테고리 × 데이터 유무)

- 폴백 전략 의사코드
- 최종 판정: "빈틈 없음" 또는 "다음 빈틈을 메워야 함: [목록]"

수학적 검증 전문가이자 QA 엔지니어로서 제시해주신 **'개인화 QT 시스템'의 아키텍처와 도메인 규칙**을 논리적·수학적으로 분석하였습니다.

현재 알고리즘의 뼈대와 시간 복잡도는 매우 훌륭하게 설계되어 있으나, **1) 요구사항 명세의 기초적인 수학적 모순, 2) 극단적 입력(Edge Cases)에 대한 예외 처리 누락, 3) 데이터 비대칭성에 의한 개인화 붕괴**라는 치명적인 빈틈(Loopholes)이 존재합니다. 

본격적인 분석에 앞서, 시스템 설계상 숨어있는 **치명적인 산술적 오류**부터 지적하겠습니다.

> **🚨 [Pre-Check] 설문 점수 산정의 수학적 모순**
> - **제시된 조건**: 12문항 중 Q1은 0점, Q2~Q12는 각 0-3점. (총점 0-27점)
> - **수학적 팩트**: Q2부터 Q12까지는 총 **11문항**입니다. $11 \text{문항} \times 3\text{점} = 33\text{점}$이 되어야 합니다.
> - **영향**: 현재 기획대로 27점을 만점으로 계산하면, 실제 유저가 28~33점을 받을 경우 매핑되는 성숙도 구간이 없어 시스템 런타임 에러(Index Out of Bounds)가 발생합니다. 문항 수를 9개로 줄이거나, 최대 성숙도 구간(심화)을 21~33점으로 확장해야 합니다.

이하 시스템의 "빈틈 없음"에 대한 6가지 항목별 논리적 증명과 최종 판정입니다.

---

### 1. 조합 완전성 (Combinatorial Completeness)
**명제:** 24가지 설정 조합($4 \times 3 \times 2$)과 140개 주제의 모든 하위 집합($2^{140}$가지) 입력에 대해 항상 유효한 30일 플랜이 생성되는가?
**증명 결과: 거짓 (False) - 빈틈 존재**

* **논리적 분석**: 수요(30일 분량)와 공급(선택된 주제의 구절 수) 간의 불균형을 처리하는 수학적 상/하한선(Cap/Floor)이 없습니다.
* **실패하는 입력 조합**:
  1. **데이터 고갈 (Underflow)**: 주제를 1개만 선택 + 분량 "많음" + 병행 "한 권씩". 해당 주제의 데이터가 15일 치 분량밖에 없다면, 16일 차부터 배열에 빈 구멍(`Null`)이 들어가 앱 크래시가 발생합니다.
  2. **데이터 초과 (Overflow)**: 140개 주제 모두 선택 + 병행 "한 권씩". 30일이라는 물리적 슬롯 안에 140개를 배정할 수 없습니다. 상위 N개만 자르는(Truncation) 로직이 없다면 인덱스 초과가 발생합니다.

### 2. 순서 유일성 (Order Uniqueness)
**명제:** 동적 페널티 알고리즘은 동일한 입력에 대해 항상 고유한 순열(Permutation)을 반환하는가? (결정론적인가?)
**증명 결과: 조건부 참 (Conditionally True)**

* **논리적 분석**: 정렬 키는 `[1. 페널티 점수 → 2. 영적 환기 우대 → 3. 발달 순서 → 4. 선택 순서]` 입니다.
* **증명**: 앞선 3개 조건이 모두 동점이더라도, 마지막 조건인 **'선택 순서(사용자가 클릭한 배열 인덱스)'**는 상호 배타적이므로 수학적으로 고유합니다. 따라서 알고리즘은 100% 결정론적입니다.
* **단, 발생하는 빈틈**: 사용자가 "일괄 선택" 버튼을 누르거나 API로 데이터를 한 번에 전송하여 '선택 순서' 값이 동일해진다면, 브라우저 JS 엔진의 정렬 안정성(Stable Sort)에 의존하게 되어 기기마다 순서가 뒤바뀌는 비결정성이 발생합니다. 이를 막기 위해 **최종 Tie-breaker(5순위)로 `Topic ID (오름차순)`를 하드코딩**해야 완벽해집니다.

### 3. 개인화 차별성 (Personalization Differentiation)
**명제:** 입력값(성숙도, 순서)이 다르면 출력되는 플랜의 경험도 유의미하게 달라지는가?
**증명 결과: 부분 실패 (데이터 의존성에 의한 착시 구간 존재)**

* **빈틈 1 (성숙도 무력화)**: 130개 주제(`curricula-extended.json`)는 가이드 없이 구절만 존재합니다. 따라서 **입문(6점) 사용자와 심화(27점) 사용자가 이 130개 중에서만 주제를 고른다면, 100% 동일한 플랜과 텍스트**를 받게 됩니다. 개인화 알고리즘이 0으로 수렴하는 치명적 맹점입니다.
* **빈틈 2 (사용자 의도 묵살)**: 사용자가 `A → B → C` 순으로 선택했더라도, 상위 조건인 '페널티'와 '발달 순서'의 가중치가 높아 시스템이 항상 `B → C → A`로 강제 재배열할 확률이 높습니다. 선택 순서 차이에 의한 플랜 변화량이 극히 적습니다.

### 4. 경계값 테스트 케이스 (Boundary Value Testing)

| 테스트 케이스 | 극한 입력 변수 | 기대 출력 (Expected) | 실제 예상 동작 및 빈틈 (Risk) |
| :--- | :--- | :--- | :--- |
| **TC-01: Zero Set** | 주제 0개 선택 | 다음 단계 진행 불가 처리 | 빈 배열을 알고리즘에 넘기면 런타임 에러 또는 무한 로딩 발생 |
| **TC-02: Max Set** | 주제 140개 전체 선택 | 30일 분량만큼 최상위 주제만 슬라이싱 | 자르기(Truncate) 기준이 없으면 140일 치 플랜이 렌더링 됨 |
| **TC-03: Mono Cat.** | 동일 카테고리만 10개 | 페널티 감수하고 발달 순서대로 배치 | 페널티 감점이 무한 누적되어 내부 점수가 음수(Underflow)로 떨어질 위험 |
| **TC-04: Boundary** | 점수 정확히 6점 vs 7점 | 6점: 입문 / 7점: 초급 | 정상 작동 (단, 총점 33점 모순 해결 전제) |
| **TC-05: Priority** | 위기 카테고리만 전체 선택 | 모두 영적 환기(`True`)로 가중치 상쇄 | 결국 3순위인 '발달 순서'에 의해서만 정렬됨 (정상 분기) |
| **TC-06: Constraint**| `is_heavy` 주제 + "짧음" 분량 | 분량을 줄이되 문맥은 보존 | **[모순 충돌]** 무거운 주제의 구절을 기계적으로 토막 내면 묵상이 불가능해지는 UX 파괴 발생 |

### 5. 데이터 의존성 맵 및 폴백(Fallback) 전략

**데이터 의존성 흐름:**
* $T \in \{1 \dots 10\} \rightarrow$ `qt-guides-topicN.json` (풀 가이드 존재 = 개인화 100%)
* $T \in \{11 \dots 140\} \rightarrow$ `curricula-extended.json` (구절만 존재 = 개인화 0%)

**폴백(Fallback) 전략 의사코드 (Pseudocode):**
풀 가이드가 없는 130개 주제를 선택한 사용자에게 '단순 성경 앱'과 똑같은 경험을 주지 않기 위해, **성숙도별 범용 묵상 질문(Generic Prompts)을 동적으로 결합**하는 방어선이 필요합니다.

```javascript
function generateDailyPlan(topicId, maturityStage, lengthPref) {
    if (hasFullGuide(topicId)) {
        return fetchFullGuide(topicId, maturityStage, lengthPref);
    } else {
        const verses = fetchVersesOnly(topicId, lengthPref);
        
        // [폴백 방어] 텍스트 공백을 심리적으로 메워주는 성숙도별 범용 템플릿
        const fallbackTemplates = {
            "입문": `오늘 읽은 말씀에서 하나님은 어떤 분으로 묘사되나요?`,
            "초급": `오늘 말씀이 내 삶과 관계에 주는 구체적인 교훈은 무엇인가요?`,
            "중급": `이 말씀의 시대적 배경을 생각하며 나의 어떤 부분을 돌아봐야 할까요?`,
            "심화": `본문의 구속사적 의미를 묵상하고, 영적 투쟁을 위한 기도를 적어보세요.`
        };
        
        return {
            verses: verses,
            guide_title: "오늘의 묵상 포인트",
            meditation_question: fallbackTemplates[maturityStage]
        };
    }
}
```

### 6. 알고리즘 복잡도 분석
* **시간 복잡도**: 30일 슬롯을 채우기 위해, 매번 남은 주제들의 카테고리 페널티를 동적으로 재계산하여 최고점을 뽑는 그리디(Greedy) 방식을 쓴다면 $\mathcal{O}(D \times N \log N)$의 복잡도를 가집니다. ($D$: 일수, $N$: 주제 수)
* **실행 성능**: $D=30$, 최대 $N=140$일 때, 연산 횟수는 약 $30 \times (140 \log_2 140) \approx 30,000$회 미만입니다. 최신 브라우저의 자바스크립트 엔진(V8)에서 3만 번의 배열 연산은 **1~2ms(밀리초) 이내에 즉시 처리**됩니다.
* **판정**: 프론트엔드 환경에서 연산하기에 성능 병목은 **전혀 없습니다.** 매우 쾌적합니다.

### 🏁 최종 판정

**최종 판정: "다음 빈틈을 메워야 함 (Not Flawless, Needs Patching)"**

동적 스케줄링 로직의 성능과 결정론적 뼈대는 훌륭하나, 수학적 무결성과 극한 상황의 안전성을 위해 프로덕션 배포 전 **다음 5가지 조치**를 반드시 적용해야 합니다.

1. **설문 점수 산술식 보정**: 11문항 × 3점 = 33점 만점에 맞추어 성숙도 구간 Boundary를 재정의하십시오.
2. **Underflow / Overflow 커팅 방어선 구축**: 30일을 채우지 못할 경우 '구절 자동 반복(Looping)'을, 초과할 경우 '상위 30일 치 슬라이싱(Truncation)' 로직을 명시하십시오.
3. **결정론적 정렬 보장**: 동적 페널티 Tie-breaker 최하단(5순위)에 `Topic ID 오름차순`을 하드코딩하여 비결정적 순서 뒤바뀜을 원천 차단하십시오.
4. **범용 폴백 템플릿 구현**: 데이터가 없는 주제에서도 성숙도별 차이를 느낄 수 있도록, 의사코드에 제시된 '성숙도별 범용 질문'을 시스템에 주입하십시오.
5. **Heavy 속성 오버라이드 룰 추가**: `is_heavy` 구절이 단일 문단(1~2절)일 때 사용자가 분량 '짧음'을 선택하면, 강제로 쪼개져 문맥이 파괴됩니다. `is_heavy`인 경우 최소 분량을 "보통"으로 보장하는 예외 처리를 추가하십시오.
