## 과제: DailyQT 시스템 아키텍처 재설계

이전 분석에서 다음 5가지 구조적 결함이 발견되었습니다:
1. 설문 점수 산술 모순 (11문항 × 3점 = 33점인데 27점 만점으로 설계)
2. Underflow/Overflow 방어 없음 (주제 1개 or 140개 선택 시)
3. 130개 주제의 개인화 0% (풀 가이드 없이 구절만 존재)
4. 메타데이터 부재 (is_heavy, is_crisis가 데이터에 없음)
5. 플랜 생성이 프론트엔드에서 이루어짐 (알고리즘 복잡도와 안 맞음)

### 현재 시스템 구조
- 스택: Node.js + Express + PostgreSQL + 프론트엔드 Vanilla JS
- 데이터: JSON 파일 (public/data/)에 정적 저장
- 온보딩: 프론트엔드에서 설문 → 점수 계산 → 플랜 생성 → API로 저장
- DB: onboarding_profiles, custom_plans, topic_progress 테이블

### 데이터 파일 현황
- topics-db.json: 140개 주제 × 8구절 (카테고리, topic_en 포함, 메타데이터 없음)
- curricula.json: 10개 주제 × 7/14/30일 (원본)
- curricula-extended.json: 129개 주제 × 30일 (구절만)
- qt-guides-topic1~10.json: 10개 주제 × 30일 × 4단계 상세 가이드
- onboarding-quiz.json: 12문항 설문

### 질문

1. **최소 변경으로 5가지 결함을 모두 해결하는 방법은?**
   - 전체 리빌드 vs 최소 패치
   - 각 결함별 구체적인 수정 사항 (파일명, 필드명, 코드 위치)
   - 수정 순서 (의존성 고려)

2. **데이터 스키마 통합 설계**
   현재 topics-db.json, curricula.json, curricula-extended.json이 분리되어 있다.
   - 하나로 합쳐야 하는가? 분리 유지가 나은가?
   - 통합한다면 최종 스키마는?
   - is_heavy, is_crisis, category_code를 어디에 어떻게 추가?
   - 140개 주제 전체의 통합 메타데이터 JSON 스키마를 제시해줘

3. **플랜 생성 알고리즘의 최적 실행 위치**
   - 프론트엔드(JS): 빠르지만 데이터 노출, 조작 가능
   - 서버(Node.js): 안전하지만 API 호출 필요
   - 하이브리드: 기본은 프론트, 복잡한 건 서버
   - 현재 아키텍처에서 가장 적은 변경으로 가능한 방법은?

4. **MVP 범위 결정**
   - 130개 주제 풀 가이드 없이 출시해도 되는가?
   - 폴백 템플릿으로 "최소 품질"이 보장되는가?
   - 아니면 최소 상위 30개 주제 가이드가 있어야 MVP인가?
   - "사용자가 실망하지 않는 최소 데이터"의 기준은?

5. **마이그레이션 계획**
   현재 이미 배포된 상태에서 구조를 바꿔야 한다.
   - 기존 사용자 데이터(onboarding_profiles, custom_plans)와의 호환성
   - 점진적 마이그레이션 vs 한번에 교체
   - 다운타임 없이 가능한가?

### 출력 형태
- 결함별 수정 방안 테이블 (문제 → 해결 → 수정 파일 → 난이도)
- 통합 메타데이터 JSON 스키마
- 플랜 생성 API 설계 (엔드포인트, 입출력)
- MVP 체크리스트 (이것만 있으면 출시 가능)
- 마이그레이션 단계별 계획 (Step 1, 2, 3...)
